# Безпека TabCalorie

[[SECURITY|Українська]] · [[SECURITY.en|English]]

Версія 1.1.0 · 2026-11-20

TabCalorie обробляє конфіденційні дані: облікові дані «Таблиці калорійності»,
секрет Nightscout і **персональні дані користувача**. Цей документ описує модель
безпеки та вимоги до публічного репозиторію.

---

## 1. Принципи

1. **Жодних секретів у репозиторії.** Реальні логіни, паролі, токени, cookies,
   email і дані харчування користувача ніколи не потрапляють у git, тести, логи чи скріншоти.
2. **Мінімізація даних.** Зберігається лише те, що потрібно для контролю
   вуглеводів і звітності.
3. **Локальність.** Усі дані зберігаються у вашій інсталяції MajorDoMo. Хмара ТК
   використовується лише для читання щоденника.
4. **Захист за замовчуванням.** Небезпечні функції (запис у ТК, Nightscout)
   вимкнені.
5. **Контроль доступу.** Читання даних і експорт вимагають прав `control_access`.

---

## 2. Зберігання секретів

| Секрет | Де зберігається | Як передається | Маскування |
|---|---|---|---|
| `PASSWORD` (ТК) | `project_modules.DATA` (серіалізований конфіг модуля) | у тілі логіну як `md5(utf8)` | `***` в UI та логах |
| `NS_API_SECRET` | `project_modules.DATA` | у заголовку `API-SECRET` як `sha1` | `***` в UI та логах |
| Cookies сесії ТК | у пам'яті під час циклу (не зберігаються у відкритому вигляді) | у заголовку `Cookie` | не логуються |

Правила:

- конфіг читається/пишеться через `getConfig()/saveConfig()`;
- пароль не дублюється у шаблонах, JS, JSON-відповідях чи URL;
- у `tabcalorie_sync_log` пишуться лише час, тип, результат, HTTP-код і
  кількість рядків — **без секретів**;
- `LAST_ERROR` очищується від можливих вкраплень секретів.

---

## 3. Захист персональних даних користувача

- Персональні дані та дані харчування зберігаються локально у таблицях `tabcalorie_*`.
- Публічна сторінка та експорт захищені перевіркою прав `control_access`.
- Експорт CSV підтримує **анонімізацію** (без імені, email тощо).
- Не публікуйте реальні дані у публічних issue, скріншотах чи демо-фікстурах.
- Для розробки та тестів використовуйте режим `demo`/фікстури без реального
  облікового запису.

## 4. Веббезпека

| Загроза | Захист |
|---|---|
| SQL-ін'єкція | усі запити через `DBSafe`/плейсхедери; жодної конкатенації користувацьких даних у SQL |
| XSS | екранування HTML у шаблонах jTemplates; виведення змінних через безпечні конструкції |
| CSRF | перевірка CSRF-токена для всіх адмін-дій (зміна конфігу, запуск синхронізації, експорт) |
| Несанкціонований доступ | перевірка прав `control_access` на публічній сторінці та в адмінці |
| Перехоплення трафіку | лише HTTPS, валідація TLS-сертифіката, заборона зниження версії |
| Витік через логи | секрети маскуються, тіла запитів із даними не пишуться у логи |
| Файлова ін'єкція | фіксовані шляхи шаблонів, без приймання шляхів від користувача |

## 5. Безпека інтеграції з API

### 5.1. «Таблиця калорійності»

- Логін і читання щоденника — через офіційний вебпортал.
- Пароль надсилається **тільки** як `md5(utf8)` у тілі логіну.
- Cookies зберігаються у пам'яті циклу, не логуються.
- Таймаути cURL і обмеження розміру відповіді захищають від «зависань».
- **Запис назад у ТК — неофіційний API**, тому:
  - `WRITEBACK_ENABLED=0` за замовчуванням;
  - `WRITEBACK_CONFIRM=1` вимагає явного підтвердження;
  - записи йдуть через окрему чергу `tabcalorie_write_queue`;
  - плагін дотримується повільного темпу (див. захист від блокування).

### 5.2. Nightscout

- `NS_ENABLED=0` за замовчуванням.
- Push здійснюється базово у `/api/v1/treatments.json`.
- У заголовку `API-SECRET` — `sha1` від `NS_API_SECRET`, не сам секрет.
- Використовуйте окремий API-ключ із мінімальними правами, якщо це можливо.

### 5.3. Захист від блокування та зловживань

- інтервал синхронізації **≥15 хвилин**;
- один запит за раз, **жодних паралельних запитів**;
- паузи ~300–500 мс між записами;
- exponential backoff і circuit breaker (`CIRCUIT_UNTIL`);
- single-flight блокування (не запускати два цикли одночасно);
- коректний `User-Agent`;
- локальний режим `demo`/фікстури для тестів без реальних запитів.

## 6. Публічний репозиторій

Перед публікацією перевірте:

```bash
# пошук можливих секретів
grep -RInE "password|api[_-]?secret|token|cookie|@gmail|@ukr|@meta" \
  --exclude-dir=.git --exclude="*.png" .

# перевірка синтаксису PHP
find . -name "*.php" -exec php -l {} \;
```

Контрольний список:

- [ ] немає реальних email/паролів/секретів;
- [ ] у прикладах використано заглушки (`user@example.org`, `changeme`);
- [ ] у скріншотах немає персональних даних;
- [ ] логи містять лише `***` замість секретів;
- [ ] `.env` і `config.local.json` виключені з пакета (`build_package.py`);
- [ ] періодично перевіряються залежності та оновлення безпеки.

---

## 7. Відповідальність

TabCalorie — інформаційний інструмент. Адміністратор інсталяції відповідає за:

- захист сервера й облікового запису MajorDoMo;
- безпечне зберігання конфігурації та резервних копій;
- контроль доступу до персональних даних користувача;
- дотримання законодавства про персональні дані;
- розуміння, що плагін **не є медичним пристроєм**.
