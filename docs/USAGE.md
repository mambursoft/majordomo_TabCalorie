# Використання TabCalorie

[[USAGE|Українська]] · [[USAGE.en|English]] · [[USAGE.ru|Русский]]

Версія 1.2.0 · 2026-11-20

Цей документ описує роботу з інтерфейсом плагіна після
[[INSTALL|встановлення]] і налаштування.

> [!WARNING]
> TabCalorie — інформаційний інструмент, **не медичний пристрій**. Усі
> рішення щодо інсуліну та лікування ухвалює лікар.

---

## 1. Загальна інформація

Публічна сторінка плагіна формується методом `run()` і шаблоном
`templates/tabcalorie/tabcalorie.html`. Вона адаптивна (CSS media queries) і
працює на мобільних та десктопних пристроях.

Мова інтерфейсу визначається ключем `LANGUAGE` (`uk` — дефолт, `en`, `ru`).

Плагін має сім вкладок:

| Вкладка | Призначення |
|---|---|
| **Огляд** | головна — поточний зріз споживання вуглеводів і прогрессбари по нормах |
| **Активність** | кроки й спалені ккал за добу та 7-денний огляд (див. розділ 11) |
| **Історія** | динаміка й порівняння за період |
| **Довідник страв** | локальний довідник страв, форма страви й пошук через autocomplete ТК |
| **Експорт** | вивантаження CSV (тепер із кроками й ккал) |
| **Діагностика** | стан системи й логи |
| **Інструкції** | довідка uk/en/ru |

## 2. Вкладка «Огляд»

Огляд відображає дані за **останню заповнену добу**. Це важливо: якщо сьогодні
заповнено лише сніданок, то обід буде порожнім, а не підтягнутим із вчорашнього
дня. Плагін не «перестрибує» через добу.

### 2.1. Що показується

- Дата (`LastDate`) і прапорець часткового заповнення (`Partial`).
- Кількість заповнених слотів із 6 (`FilledSlots`).
- Шість прийомів їжі з вуглеводами (г) і калоріями:
  1. Сніданок — 2. Перекус — 3. Обід — 4. Підвечірок — 5. Вечеря — 6. Друга вечеря.
- Групи:
  - **Основні прийоми** (1+3+5) — `GroupMainCarbs`;
  - **Перекуси** (2+4+6) — `GroupSnacksCarbs`;
  - **Добова сума** — `GroupDayCarbs`.
- Добові підсумки: вуглеводи, калорії, білки, жири, клітковина, цукри, ХО, GI.
- Ціль (`CARBS_TARGET`) і відсоток її виконання; залишок ліміту.
- Прогресбари по нормах для кожного з 6 прийомів їжі (див. розділ 2.5).

### 2.2. ХО (хлібні одиниці)

`TotalXE` розраховується як `TotalCarbs / GRAMS_PER_XE`. За замовчуванням
1 ХО = 10 г вуглеводів. Якщо лікар використовує 12 г — змініть `GRAMS_PER_XE`
у налаштуваннях.

### 2.3. Типовий chart

Кнопка **«Створити типовий chart»** генерує графік споживання (сніданок, обід,
вечеря, підсумок за добу) через стандартний механізм MajorDoMo (Highcharts або
pChart). Графік створюється на основі даних об'єкта `TabCalorie` і таблиці
`tabcalorie_days`.

### 2.4. Об'єкт MajorDoMo `TabCalorie`

Клас `STabCalorie`. Властивості читаються через `gg('TabCalorie.Властивість')`,
наприклад:

```php
$carbs = gg('TabCalorie.TotalCarbs');
$xe    = gg('TabCalorie.TotalXE');
$date  = gg('TabCalorie.LastDate');
```

| Властивість | Опис |
|---|---|
| `LastDate` | Дата останньої заповненої доби |
| `Partial` | Частково заповнена доба |
| `FilledSlots` | Кількість заповнених слотів (0–6) |
| `Slot1Carbs` … `Slot6Carbs` | Вуглеводи (г) по слотах |
| `Slot1Kcal` … `Slot6Kcal` | Калорії по слотах |
| `GroupMainCarbs` | 1+3+5 |
| `GroupSnacksCarbs` | 2+4+6 |
| `GroupDayCarbs` | Добова сума вуглеводів |
| `TotalCarbs`, `TotalKcal`, `TotalProtein`, `TotalFat`, `TotalFiber`, `TotalSugar`, `TotalXE`, `GI`, `Notes`, `Updated` | Підсумки та метадані |
| `status` | `1`, коли інтеграція здорова; `0` при будь-якій інтеграційній проблемі (`LAST_ERROR`, відкритий circuit breaker) або коли вимкнено фоновий цикл (`SYNC_ENABLED=0` чи `cycle_tabcalorieRun` старший за ~10 хв). |
| `raw` | JSON із усіма даними від початку останньої доби, за яку є хоча б один запис: сирий щоденник ТК + нормалізовані записи. |
| `ActivitySteps`, `ActivityKcal`, `ActivityCount` | Агрегат активності за останню заповнену добу (кроки, спалені ккал, кількість). |

> [!NOTE]
> Детальніше про `status` і `raw` — у розділі 13; про ротацію логів і TTL черги — у розділі 14.

Ви можете використовувати ці властивості у сценаріях MajorDoMo, наприклад, щоб
надіслати повідомлення при перевищенні цілі.

### 2.5. Норми споживання та прогресбари

Добові норми задаються ключами конфігурації:

| Ключ | За замовчуванням | Призначення |
|---|---|---|
| `CALORIES_TARGET` | `1800` | Добова норма калорій, ккал |
| `PROTEIN_TARGET` | `90` | Добова норма білків, г |
| `FAT_TARGET` | `60` | Добова норма жирів, г |
| `CARBS_TARGET` | `120` | Добова норма вуглеводів, г |
| `MEAL_NORM_SHARE` | `25` (діапазон 10–50, %) | Частка основного прийому їжі (сніданок/обід/вечеря) від добової норми; решта норми ділиться порівну між перекусами (2, 4, 6) |

Норма основного прийому = `добова норма × MEAL_NORM_SHARE / 100`; норма перекусу =
`добова норма × (100 − MEAL_NORM_SHARE) / 300`. За `MEAL_NORM_SHARE=25` основні
прийоми отримують по 25% добової норми, а перекуси — по ~8,33%.

> [!IMPORTANT]
> Якщо норми заповнені (не 0), у вкладці **Огляд** для кожного з 6 прийомів їжі
> показується прогресбар по вуглеводах, калоріях, білках і жирах відносно
> розрахованої норми прийому; перевищення виділяється кольором.

## 3. Вкладка «Історія»

- Добові підсумки за вибраний період із таблиці `tabcalorie_days`.
- Порівняння з попередніми днями/тижнями.
- Тренд і відхилення від цілі (`CARBS_TARGET`).
- Перехід до деталей конкретного дня (записи з `tabcalorie_entries`).

Дані беруться з локальної БД, тому історія доступна навіть без з'єднання з ТК.

---

## 4. Вкладка «Довідник»

API «Таблиці калорійності» **не віддає глікемічний індекс (GI) і нотатки на рівні
страви** (нотатки є лише на рівні слота). Тому плагін веде власний довідник у
таблиці `tabcalorie_foods`.

- Унікальні страви з полем `guid`.
- Поживні значення **на 100 г**: білки, жири, вуглеводи, клітковина, цукри, калорії.
- Редаговані поля `GI` і `Notes`.
- Можна додавати локальні записи з `source=manual` — вони **не** синхронізуються
  назад у ТК.

> [!NOTE]
> Локальні правки GI/нотаток зберігаються і не перезаписуються автоматичною
> синхронізацією (захист ручних правок).

### 4.1. Форма страви та службові дані (v1.2.0)

У вкладці **Довідник страв** додано форму додавання/редагування страви:

- [ ] назва, ID, URL, одиниця, грами, слот (1..6);
- [ ] БЖУ/ккал на 100 г, ГІ, нотатки;
- [ ] пошук страви через autocomplete ТК;
- [ ] службові поля: `FOOD_ID` (guid для API), `FOOD_URL` (шлях `potraviny/...`),
  `UNIT_GUID` (за замовчуванням `0000000000000001`), `UNIT_OPTIONS` (JSON
  доступних одиниць із множниками), `DEFAULT_MULTIPLIER` (грами за
  замовчуванням), `DEFAULT_SLOT` (1..6), `SERVICE_JSON` (сира відповідь форми ТК).

> [!TIP]
> Write-back у ТК використовує ці дані страви, а не жорстко задані значення.

## 5. Вкладка «Експорт»

Формується CSV-файл із персональними даними користувача — дотримуйтеся обережності.

| Параметр | Значення |
|---|---|
| Період | день / тиждень / місяць / рік |
| Кодування | UTF-8 із BOM (коректне відкриття в Excel) |
| Розділювач | `;` (`CSV_DELIMITER`, сумісний з українським Excel) |
| Формат дат | `ДД.ММ.РРРР` |
| Вміст | добові суми, ХО, кроки й спалені ккал, за потреби деталі страв |
| Безпека | без секретів; можлива анонімізація |

Експорт захищений перевіркою прав `control_access`. Для передачі даних
використовуйте анонімізований варіант (без імені, email тощо).

## 6. Вкладка «Діагностика»

- Результат кнопки **«Перевірити підключення»**: DNS/TLS/HTTP, логін, cookies,
  ендпоїнт, парсинг JSON.
- Час останньої успішної синхронізації (`LAST_SYNC`).
- Остання помилка (`LAST_ERROR`, без секретів).
- Стан circuit breaker (`CIRCUIT_UNTIL`).
- Журнал таблиці `tabcalorie_sync_log`: час, тип, результат, HTTP-код, кількість рядків.
- Пояснення типових помилок і посилання на інструкцію «Забули пароль?».

## 8. Синхронізація: як це працює

1. Фоновий цикл `scripts/cycle_tabcalorie.php` запускається за розкладом
   (рекомендовано кожні 15–60 хв; `SYNC_INTERVAL_MIN`, мінімум 15).
2. Логін: `POST /login/create?format=json&voucher=false`, тіло з `md5(пароль)`;
   cookies з `Set-Cookie` зберігаються і повертаються у `Cookie`.
3. Для кожного з останніх `SYNC_DAYS` днів виконується
   `GET /user/diary/ДД.ММ.РРРР/get?format=json`.
4. Розбираються 6 слотів, добові суми (`carbohydrateTotal`, `sugarTotal`,
   `fiberTotal`, `proteinTotal`, `fatTotal`, `energyTotal`) та активність
   `data.activities` (за `ACTIVITY_ENABLED=1`).
5. Записи зберігаються ідемпотентно за унікальним ключем
   `date + slot + food_guid + unit_raw` (`INSERT ... ON DUPLICATE KEY UPDATE`).
6. Оновлюються `tabcalorie_days` (включно з `STEPS`, `ACTIVITY_KCAL`,
   `ACTIVITY_COUNT`), `tabcalorie_activities`, об'єкт `TabCalorie` і
   `tabcalorie_sync_log`.

### Захист від блокування

- один запит за раз, без паралельних викликів;
- паузи ~300–500 мс між записами;
- exponential backoff при помилках;
- single-flight блокування (не запускати два цикли одночасно);
- таймаути й обмеження розміру відповіді;
- circuit breaker (`CIRCUIT_UNTIL`) після серії помилок;
- коректний `User-Agent`.

---

## 9. Додаткові можливості

- **Хук**: при зміні властивості `HOOK_PROPERTY` запускається примусове
  оновлення з дебаунсом `HOOK_DEBOUNCE_SEC` (захист від петель).
- **Nightscout**: за `NS_ENABLED=1` робиться базовий push у
  `/api/v1/treatments.json` (заголовок `API-SECRET` = `sha1` від `NS_API_SECRET`).
  Вимкнено за замовчуванням.
- **Write-back у ТК**: за `WRITEBACK_ENABLED=1` і `WRITEBACK_CONFIRM=1` записи
  потрапляють у чергу `tabcalorie_write_queue`. Неофіційний API, вимкнено за
  замовчуванням.
- **Зберігання**: рядки старші за `RETENTION_DAYS` (1825 днів) видаляються щодня.
- **Активність**: `ACTIVITY_ENABLED=1` — імпорт `data.activities` (див. розділ 11).
- **Ротація логів**: `LOG_RETENTION_DAYS=30` і `LOG_MAX_ROWS=2000` для
  `tabcalorie_sync_log`.
- **TTL черги**: `WRITE_QUEUE_TTL_DAYS=7` для `tabcalorie_write_queue`.

---

## 10. Поради

- Не покладайтеся на плагін як на єдине джерело даних — ТК залишається
  основним щоденником.
- Перевіряйте **Діагностику** після зміни пароля ТК.
- Для передачі даних формуйте анонімізований CSV.
- Якщо API тимчасово недоступний, дані залишаються в локальній БД.

## 11. Вкладка «Активність» (v1.2.0)

У застосунку ТК увімкнено інтеграцію з Health Connect, тому щоденник ТК повертає
поле `data.activities` із записами активності: `steps` (кроки), `energy` (спалені
калорії), `title`, `type`, `activityType`, тривалість тощо.

За `ACTIVITY_ENABLED=1` (за замовчуванням) плагін:

- [ ] зберігає активність у `tabcalorie_activities` (унікальний ключ — дата + ID активності);
- [ ] агрегує `STEPS`, `ACTIVITY_KCAL`, `ACTIVITY_COUNT` у `tabcalorie_days`;
- [ ] показує вкладку **Активність**: добовий зріз і 7-денний огляд (кроки, ккал);
- [ ] додає кроки й спалені ккал до CSV-експорту.

> [!WARNING]
> Health Connect у ТК односторонній: активність іде у щоденник ТК, а плагін лише
> зчитує її звідти. Плагін не пише в Health Connect нічого.

## 12. Службові дані страви для write-back (v1.2.0)

Див. розділ 4.1. Поля `FOOD_ID`, `FOOD_URL`, `UNIT_GUID`, `UNIT_OPTIONS`,
`DEFAULT_MULTIPLIER`, `DEFAULT_SLOT`, `SERVICE_JSON` зберігаються у
`tabcalorie_foods`; write-back у ТК бере з них guid, URL, одиницю, множник і слот
замість жорстко заданих значень.

## 13. Стан і сирі дані: `status`, `raw` (v1.2.0)

| Властивість | Опис |
|---|---|
| `status` | `1`, коли інтеграція здорова; `0` при будь-якій інтеграційній проблемі (`LAST_ERROR`, відкритий circuit breaker) або коли вимкнено фоновий цикл (`SYNC_ENABLED=0` чи `cycle_tabcalorieRun` старший за ~10 хв). |
| `raw` | JSON із усіма даними від початку останньої доби, за яку є хоча б один запис: сирий щоденник ТК + нормалізовані записи. |
| `ActivitySteps`, `ActivityKcal`, `ActivityCount` | Агрегат активності за останню заповнену добу. |

## 14. Ротація логів і TTL черги (v1.2.0)

- [ ] `LOG_RETENTION_DAYS` (30) — видалення рядків `tabcalorie_sync_log` старших
  за N днів.
- [ ] `LOG_MAX_ROWS` (2000) — обмеження кількості рядків `tabcalorie_sync_log`;
  зайві найстаріші рядки видаляються.
- [ ] `WRITE_QUEUE_TTL_DAYS` (7) — рядки `tabcalorie_write_queue` старші за
  термін актуальності видаляються автоматично під час cleanup.
