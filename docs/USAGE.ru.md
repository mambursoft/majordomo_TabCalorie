# Использование TabCalorie

[[USAGE|Українська]] · [[USAGE.en|English]] · [[USAGE.ru|Русский]]

Версия 1.1.0 · 2026-11-20

Этот документ описывает работу с интерфейсом плагина после
[[INSTALL.ru|установки]] и настройки.

> [!WARNING]
> TabCalorie — информационный инструмент, **не медицинский прибор**. Все
> решения по инсулину и лечению принимает врач.

---

## 1. Общая информация

Публичная страница плагина формируется методом `run()` и шаблоном
`templates/tabcalorie/tabcalorie.html`. Она адаптивна (CSS media queries) и
работает на мобильных и десктопных устройствах.

Язык интерфейса определяется ключом `LANGUAGE` (`uk` — по умолчанию, `en`, `ru`).

Плагин имеет шесть вкладок:

| Вкладка | Назначение |
|---|---|
| **Обзор** | главная — текущий срез потребления углеводов и прогрессбары по нормам |
| **История** | динамика и сравнение за период |
| **Справочник** | локальный справочник блюд |
| **Экспорт** | выгрузка CSV |
| **Диагностика** | состояние системы и логи |
| **Инструкции** | справка uk/en/ru |

## 2. Вкладка «Обзор»

Обзор отображает данные за **последний заполненный день**. Это важно: если
сегодня заполнен только завтрак, обед будет пустым, а не подтянутым из вчерашнего
дня. Плагин не «перепрыгивает» через день для слота.

### 2.1. Что отображается

- Дата (`LastDate`) и флаг частичного заполнения (`Partial`).
- Количество заполненных слотов из 6 (`FilledSlots`).
- Шесть приёмов пищи с углеводами (г) и калориями:
  1. Завтрак — 2. Перекус — 3. Обед — 4. Полдник — 5. Ужин — 6. Второй ужин.
- Группы:
  - **Основные приёмы** (1+3+5) — `GroupMainCarbs`;
  - **Перекусы** (2+4+6) — `GroupSnacksCarbs`;
  - **Суточная сумма** — `GroupDayCarbs`.
- Суточные суммы: углеводы, калории, белки, жиры, клетчатка, сахара, ХЕ, GI.
- Цель (`CARBS_TARGET`), процент выполнения и остаток лимита.
- Прогрессбары по нормам для каждого из 6 приёмов пищи (см. раздел 2.5).

### 2.2. ХЕ (хлебные единицы)

`TotalXE` рассчитывается как `TotalCarbs / GRAMS_PER_XE`. По умолчанию
1 ХЕ = 10 г углеводов. Если врач считает 12 г — измените `GRAMS_PER_XE`
в настройках.

### 2.3. Типовой chart

Кнопка **«Создать типовой chart»** генерирует график потребления (завтрак, обед,
ужин, сумма за день) через стандартный механизм MajorDoMo (Highcharts или
pChart). График строится на основе объекта `TabCalorie` и таблицы
`tabcalorie_days`.

### 2.4. Объект MajorDoMo `TabCalorie`

Класс `STabCalorie`. Свойства читаются через `gg('TabCalorie.Свойство')`,
например:

```php
$carbs = gg('TabCalorie.TotalCarbs');
$xe    = gg('TabCalorie.TotalXE');
$date  = gg('TabCalorie.LastDate');
```

| Свойство | Описание |
|---|---|
| `LastDate` | Дата последнего заполненного дня |
| `Partial` | Флаг частично заполненного дня |
| `FilledSlots` | Количество заполненных слотов (0–6) |
| `Slot1Carbs` … `Slot6Carbs` | Углеводы (г) по слотам |
| `Slot1Kcal` … `Slot6Kcal` | Калории по слотам |
| `GroupMainCarbs` | 1+3+5 |
| `GroupSnacksCarbs` | 2+4+6 |
| `GroupDayCarbs` | Суточная сумма углеводов |
| `TotalCarbs`, `TotalKcal`, `TotalProtein`, `TotalFat`, `TotalFiber`, `TotalSugar`, `TotalXE`, `GI`, `Notes`, `Updated` | Суммы и метаданные |

Эти свойства можно использовать в сценариях MajorDoMo, например, чтобы
отправить уведомление при превышении цели.

### 2.5. Нормы потребления и прогрессбары

Суточные нормы задаются ключами конфигурации:

| Ключ | По умолчанию | Назначение |
|---|---|---|
| `CALORIES_TARGET` | `1800` | Суточная норма калорий, ккал |
| `PROTEIN_TARGET` | `90` | Суточная норма белков, г |
| `FAT_TARGET` | `60` | Суточная норма жиров, г |
| `CARBS_TARGET` | `120` | Суточная норма углеводов, г |
| `MEAL_NORM_SHARE` | `25` (диапазон 10–50, %) | Доля основного приёма пищи (завтрак/обед/ужин) от суточной нормы; остаток нормы делится поровну между перекусами (2, 4, 6) |

Норма основного приёма = `суточная норма × MEAL_NORM_SHARE / 100`; норма перекуса =
`суточная норма × (100 − MEAL_NORM_SHARE) / 300`. При `MEAL_NORM_SHARE=25` основные
приёмы получают по 25% суточной нормы, а перекусы — по ~8,33%.

> [!IMPORTANT]
> Если нормы заполнены (не 0), на вкладке **Обзор** для каждого из 6 приёмов пищи
> отображается прогрессбар по углеводам, калориям, белкам и жирам относительно
> рассчитанной нормы приёма; превышение выделяется цветом.

## 3. Вкладка «История»

- Суточные суммы за выбранный период из таблицы `tabcalorie_days`.
- Сравнение с предыдущими днями/неделями.
- Тренд и отклонение от цели (`CARBS_TARGET`).
- Переход к деталям конкретного дня (записи из `tabcalorie_entries`).

Данные берутся из локальной БД, поэтому история доступна даже без связи с ТК.

---

## 4. Вкладка «Справочник»

API «Таблицы калорийности» **не возвращает гликемический индекс (GI) и заметки
на уровне блюда** (заметки есть только на уровне слота). Поэтому плагин ведёт
собственный справочник в таблице `tabcalorie_foods`.

- Уникальные блюда с полем `guid`.
- Пищевые ценности **на 100 г**: белки, жиры, углеводы, клетчатка, сахара, калории.
- Редактируемые поля `GI` и `Notes`.
- Можно добавлять локальные записи с `source=manual` — они **не** синхронизируются
  обратно в ТК.

> [!NOTE]
> Локальные правки GI/заметок сохраняются и не перезаписываются автоматической
> синхронизацией (защита ручных правок).

## 5. Вкладка «Экспорт»

Формируется CSV-файл с персональными данными пользователя — соблюдайте осторожность.

| Параметр | Значение |
|---|---|
| Период | день / неделя / месяц / год |
| Кодировка | UTF-8 с BOM (корректно открывается в Excel) |
| Разделитель | `;` (`CSV_DELIMITER`, совместим с украинским Excel) |
| Формат дат | `ДД.ММ.ГГГГ` |
| Содержание | суточные суммы, ХЕ, при необходимости детали блюд |
| Безопасность | без секретов; возможна анонимизация |

Экспорт защищён проверкой прав `control_access`. Для передачи данных
используйте анонимизированный вариант (без имени, email и т.п.).

## 6. Вкладка «Диагностика»

- Результат кнопки **«Проверить подключение»**: DNS/TLS/HTTP, логин, cookie, эндпоинт, парсинг JSON.
- Время последней успешной синхронизации (`LAST_SYNC`).
- Последняя ошибка (`LAST_ERROR`, без секретов).
- Состояние circuit breaker (`CIRCUIT_UNTIL`).
- Журнал таблицы `tabcalorie_sync_log`: время, тип, результат, HTTP-код, количество строк.
- Пояснения типовых ошибок и ссылка на инструкцию «Забыли пароль?».

## 8. Как работает синхронизация

1. Фоновый цикл `scripts/cycle_tabcalorie.php` запускается по расписанию
   (рекомендовано 15–60 мин; `SYNC_INTERVAL_MIN`, минимум 15).
2. Логин: `POST /login/create?format=json&voucher=false` с `md5(пароль)`;
   cookie из `Set-Cookie` сохраняются и возвращаются в `Cookie`.
3. Для каждого из последних `SYNC_DAYS` дней выполняется
   `GET /user/diary/ДД.ММ.ГГГГ/get?format=json`.
4. Разбираются 6 слотов и суточные суммы (`carbohydrateTotal`, `sugarTotal`,
   `fiberTotal`, `proteinTotal`, `fatTotal`, `energyTotal`).
5. Записи сохраняются идемпотентно по уникальному ключу
   `date + slot + food_guid + unit_raw` (`INSERT ... ON DUPLICATE KEY UPDATE`).
6. Обновляются `tabcalorie_days`, объект `TabCalorie` и `tabcalorie_sync_log`.

### Защита от блокировки

- один запрос за раз, без параллельных вызовов;
- паузы ~300–500 мс между записями;
- exponential backoff при ошибках;
- single-flight блокировка (не запускать два цикла одновременно);
- таймауты и ограничение размера ответа;
- circuit breaker (`CIRCUIT_UNTIL`) после серии ошибок;
- корректный `User-Agent`.

## 9. Дополнительные возможности

- **Хук**: при изменении свойства `HOOK_PROPERTY` запускается принудительное
  обновление с дебаунсом `HOOK_DEBOUNCE_SEC` (защита от петель).
- **Nightscout**: при `NS_ENABLED=1` выполняется базовый push в
  `/api/v1/treatments.json` (заголовок `API-SECRET` = `sha1` от `NS_API_SECRET`).
  По умолчанию отключено.
- **Запись в ТК**: при `WRITEBACK_ENABLED=1` и `WRITEBACK_CONFIRM=1` записи
  попадают в очередь `tabcalorie_write_queue`. Неофициальный API, по умолчанию
  отключён.
- **Хранение**: строки старше `RETENTION_DAYS` (1825 дней) удаляются ежедневно.

---

## 10. Советы

- Не полагайтесь на плагин как на единственный источник данных — ТК остаётся
  основным дневником.
- Проверяйте **Диагностику** после смены пароля ТК.
- Для передачи данных формируйте анонимизированный CSV.
- Если API временно недоступен, данные остаются в локальной БД.
